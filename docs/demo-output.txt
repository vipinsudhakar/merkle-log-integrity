  [5]  TAMPER DETECTION AND LOCALISATION
------------------------------------------------------------------------------
  entry #171 edited
    before : "sensor read ok, value nominal"
    after  : "heartbeat ok"

  a single changed byte propagates all the way to the super-root:
    super-root before : a3072b86b86daf0290dc335f383ede06feb62094da031b466cbaa6be3986bf80
    super-root after  : faf6541f64ac7de30dd96959993cce4c46a562f3bea045f586673573edcdd449
    identical?        : NO - tampering detected

  what the old proof does and does not still prove:
    original entry + old proof vs OLD (trusted) root : VALID
    original entry + old proof vs NEW root           : INVALID
    forged   entry + old proof vs OLD (trusted) root : INVALID
    forged   entry + old proof vs NEW root           : VALID

    Read the last line carefully - it is the honest limit of the scheme,
    and the thing worth being able to explain. An attacker who rewrites an
    entry AND recomputes the tree gets a set that is internally consistent:
    the forged entry verifies against the forged root. What they cannot do
    is make it verify against the TRUSTED root (line 3: INVALID). That is
    why the super-root has to be anchored outside the log - published,
    signed, or held by the verifier - not just stored beside the data.

  LOCALISATION - narrowing to the culprit without scanning entries:
    step 1: compare 8 chunk roots      -> chunk 2 differs
    step 2: descend that chunk's tree  -> local leaf 42
    step 3: global entry index         -> 170  (entry #171)
    comparisons used: 14, against 512 entries in the dataset

------------------------------------------------------------------------------
  [6]  LOCALISED REBUILD COST
------------------------------------------------------------------------------
  When an entry changes, only its own chunk's tree is rebuilt, plus the
  small super-tree over the chunk roots. Every other chunk is untouched.

    chunk rebuilt              : 2
    entries re-hashed          : 64
    entries in the dataset     : 512
    saving vs one global tree  : 8.0x cheaper

  This is exactly why chunking strategy matters, and what Phase 7 measures:
  smaller chunks rebuild faster but make proofs longer, and vice versa.

------------------------------------------------------------------------------
  [7]  CHUNKING STRATEGY COMPARISON  (the contribution over the base paper)
------------------------------------------------------------------------------
  strategy     chunks   avg size   avg steps   proof bytes   rebuild cost
  --------     ------   --------   ---------   -----------   ------------
  fixed-size   8        64.0       9.00        288           64.0 entries
  time-window  45       11.4       10.04       321           23.2 entries
  entropy      28       18.3       9.39        301           18.9 entries

  Reading it: fewer, larger chunks -> shorter super-tree path but a taller
  chunk tree and a costlier rebuild. The three strategies land at different
  points on that trade-off, which is what the base paper's single strategy
  could not show. Base-paper reference proof size: ~1006 bytes.

  KNOWN LIMITATION (stated, not hidden): Shannon entropy over a short byte
  window is biased low and noisy, so on short log payloads the entropy
  boundary signal degrades toward arbitrary. Guarded with min/max chunk
  size so a low-entropy run cannot collapse into one giant chunk.
